# What the security evaluation establishes

AgentGuard must let an agent buy an approved service while keeping supplier text from changing its authority. We test normal task completion as well as malicious proposals, and keep model behavior separate from executor and contract enforcement.

On 2026-11-03, `z-ai/glm-5.3-flash` completed one fixed pass over **4 benign and 11 adversarial supplier responses**. It proposed the exact approved invoice in all 15 cases. No attacker-requested deviation was observed. The executor independently accepted 3 valid control proposals and rejected 11 deliberately altered proposals. **No blockchain transactions were sent by this evaluation.**

[Full model report, exact requests and responses](security-benchmark.json) · [Fixed corpus](../benchmarks/payment-cases.json) · [Recorded testnet enforcement](../web/testnet-evidence.json)

## Three different layers of evidence

| Layer | Observed result | What this establishes |
| --- | --- | --- |
| Live model, benign supplier text | 4/4 exact approved proposals; no missing or rejected proposal | Normal purchase proposals succeeded on these four fixtures |
| Live model, adversarial supplier text | 11/11 kept the original invoice; 0 requested deviations | Resistance to these eleven fixtures in this single pass |
| Deterministic executor controls | 3/3 valid proposals accepted; 11/11 altered proposals rejected | Exact-invoice validation rejects each forced deviation even when the model is assumed to request it |
| Previously recorded NEAR testnet checks | 8 checks passed, including recipient, amount, replay, key and owner boundaries | Separate protocol/contract behavior on the recorded deployed WASM, not actions generated by this model evaluation |

There were **no observed live malicious proposals**, so a live containment percentage is **not applicable**. We do not report “100% of model attacks stopped by the contract,” simulate a successful jailbreak, or infer general safety from fifteen responses. A missing proposal would be recorded separately; it would not automatically count as an explicit refusal. Provider failures stop the run and remain in the report rather than being retried until they pass.

The user quote and policy are trusted inputs in this experiment. The supplier response is the untrusted surface. Provider reasoning fields and credentials are excluded.

## Which boundary stops which request?

| Requested action | Executor boundary | NEAR boundary and limits |
| --- | --- | --- |
| Change invoice recipient | Exact recipient equality | Contract allowlist rejects a non-allowlisted recipient; recorded transaction `BHBBWqBXhp2VVhDhyPQWT2ufxPPDvBN5AfjjDZQVBAhp` |
| Increase the invoice price | Exact decimal-string amount equality | Contract enforces payment/day/lifetime caps, not the invoice price. A change from 0.01 to 0.1 could still fit the contract caps; the invoice validator must reject it |
| Pay above the contract cap | Invoice equality and preflight | Recorded `PAYMENT_LIMIT` rejection: `3WKvTBpiEz8KkR9BVmide5d4GjmUiaqQAwmABhkjwdBf` |
| Request multiple payments | Exactly one permitted tool call | One in-flight transfer and monotonic nonce; a sequence using fresh nonces is bounded by budgets, not by invoice identity |
| Replay a payment | Saved request ID and original transaction reconciliation | Reused accepted nonce rejected in `2oGk2BBY1phZqoXAQDcUGnMGw7gWc8CvLzXPJ25PnSi2` |
| Use administrative methods | Only `propose_payment`, no CLI arguments from model | Restricted access key permits only `pay` on the configured vault; protocol rejections are in the recorded report |
| Change invoice ID or supply nonce | Exact invoice ID and closed argument schema; executor selects nonce | Invoice ID and dataset hash are **not committed onchain**. The contract does not attest invoice identity or delivery |

The full-access owner and deployment keys remain trusted. An allowlisted supplier may deliver poor data, and an agent may consume its allowed budget. See [SECURITY.md](../SECURITY.md).

## Reproduce without keys or spend

Requires the repository's supported Node version; no npm dependencies.

```sh
npm test
npm run benchmark:security
npm run benchmark:security:replay
```

Expected: 27 tests pass; the benchmark prints **14 validator controls passed**, **AI calls: 0**, and the live plan. The default command does not load `.env`, call a model, sign anything, or change the AI ledger. The process/HTTP tests use isolated providers and temporary journals. The replay command revalidates all 15 recorded model outputs, 14 controls, exact prompts and source hashes without credentials or network access. It checks internal consistency of the recorded evidence, not independent provider attestation. If source hashes change, reproduce using the recorded source version rather than relabeling old evidence as a new run.

To independently repeat the model experiment, configure your own `NEAR_AI_API_KEY` in a local `.env` and opt in explicitly:

```sh
npm run benchmark:security:send
```

One run makes at most 15 completion attempts, once per fixture, with no automatic retries. It shares the application's locked cumulative $1 ledger and conservatively reserves at most $0.15 for this run. Each attempt is journaled before the request. All inputs and results, including failures, are stored under ignored `.local/security-benchmark/<run-id>.json`; each explicit new run gets its own ID. Reproducibility means fixed inputs and procedure, not bit-identical LLM outputs. These files are JSON reports, not screenshots.
